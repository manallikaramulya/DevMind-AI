I recalled our architecture decision from Commit #84 regarding PostgreSQL connection pooling on ShopSphere:

Persistent Memory #MEM-004: DB Session Lifecycle Rule

In our architecture, get_db holds the transaction lock. Because process_order_batch() performs an asynchronous I/O batch (averaging 4.2s), the DB connection remains checked out from the pool while awaiting the worker, exhausting the 5 connection limit.

Solution: Release the database session back to the pool before running the background processing, or run the query inside a scoped context manager:

python (Recommended Fix) 
@router.get("/orders/stream")
async def stream_orders():
    # 1. Fetch orders in an immediate scoped session
    async with async_session_factory() as db:
        result = await db.execute(select(Order).where(Order.status == "pending"))
        orders = result.scalars().all()
    # 2. Connection is immediately released back to QueuePool here!
    
    # 3. Heavy I/O processing proceeds without hogging DB connections
    await process_order_batch(orders)
    return {"count": len(orders)}

This will prevent pool starvation under concurrent requests while preserving our established PostgreSQL connection ceiling.
